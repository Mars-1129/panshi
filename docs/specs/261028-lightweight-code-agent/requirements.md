# 需求文档：轻量 Coding Agent

## 1. 背景

当前 Blade Agent 已经验证了几项适合复用的架构思想：协议与业务分层、Agent Loop 与平台能力分离、工具调用产生可观察事件、执行环境可以独立于业务服务，以及 SDK/CLI/Web 共享同一套会话语义。

本项目不复制 Blade Agent 的完整平台，而是提炼其中适合轻量产品的部分，面向个人开发者和小型团队，提供一条可控的代码工作闭环：

```text
理解仓库 → 生成计划 → 审批 → 修改 → 测试/构建 → 修复或交付证据
```

## 2. 产品定位

工作名：**RepoPilot Lite**。

产品承诺：

> 让 Agent 能在真实代码仓库中完成小到中等规模的开发任务，并清楚说明它改了什么、验证了什么、还剩什么风险。

核心特征：

1. **本地优先**：代码默认留在用户机器，模型只收到任务所需上下文。
2. **仓库优先**：先读取仓库规则、入口、依赖和测试，再开始修改。
3. **diff 优先**：所有写入都可审查、可撤销，不直接覆盖用户工作区。
4. **测试闭环**：修改必须绑定验证命令和结果。
5. **单 Agent 起步**：通过 Plan/Act 两阶段获得可控性，不以多 Agent 作为卖点。

## 3. 目标用户

- 需要快速完成小型功能和重复性维护的个人开发者。
- 希望把 Issue、失败测试和 PR 审查半自动化的小团队。
- 需要生成标准项目骨架，但不希望把所有设计决策交给模型的技术负责人。

## 4. 用户任务

### 4.1 代码生成

用户用自然语言描述目标，Agent 识别相关模块、提出计划、修改工作树并运行最小验证。

### 4.2 代码审查

用户指定当前 diff、分支或提交范围，Agent 只读分析问题，输出带文件和行号的发现，不修改代码。

### 4.3 Bug 修复

用户提供失败命令、错误日志、Issue 或复现步骤，Agent 先尝试复现，再修改代码和测试；无法复现时必须显式标记假设。

### 4.4 自动化测试

Agent 根据仓库已有测试框架生成或补充测试，执行测试、Lint、类型检查和构建，并解释失败原因。

### 4.5 项目脚手架

Agent 从确定性模板生成项目目录、依赖和基础测试，再根据用户需求填充业务差异。

## 5. 功能需求

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-01 | 仓库识别 | 识别主要语言、包管理器、入口、测试命令和规则文件，并生成摘要 |
| FR-02 | 上下文选择 | 只读取与任务相关的文件；输出引用的文件清单 |
| FR-03 | 计划模式 | 写入前给出目标、文件、步骤、风险和验证方案 |
| FR-04 | 变更隔离 | 默认在 Git worktree 或临时分支中修改 |
| FR-05 | 文件修改 | 支持创建、编辑、重命名和删除，所有操作可生成 diff |
| FR-06 | 命令执行 | 支持受控执行，并记录命令、退出码、输出截断和耗时 |
| FR-07 | 测试闭环 | 修改后执行目标测试；失败时可进入有限次数的修复循环 |
| FR-08 | 代码审查 | 每个问题关联文件、行号、严重级别、理由和建议 |
| FR-09 | 脚手架 | 模板生成后自动安装依赖并运行基础检查 |
| FR-10 | 审批 | 写文件、删除文件、外部网络、发布和高风险命令可独立审批 |
| FR-11 | 可撤销 | 每次写入前生成 checkpoint，可以恢复到任务开始或任一稳定点 |
| FR-12 | 运行记录 | 任务结束后保留计划、事件、diff、命令和验证结果 |
| FR-13 | 无头模式 | 能在 CI 中读取输入并输出 JSONL，不依赖交互式终端 |
| FR-14 | 规则文件 | 支持仓库级 Agent 规则，并明确规则来源和优先级 |

## 6. 非功能需求

### 安全与可靠性

- 默认不能读取 `.env`、私钥、证书、云凭据和 Git ignored secrets。
- 执行命令限制在当前工作区，设置超时、输出大小和并发上限。
- 默认不执行 `git push`、发布、部署、删除工作区和修改主分支。
- 所有模型生成的路径和命令在执行前进行校验。
- 任务失败时保留现场和日志，不自动清理用户可能需要的证据。

### 可移植性

- 第一版支持 Windows、macOS、Linux。
- 不依赖 Bash 特性作为核心能力。
- 测试命令从项目配置推断，不能假设所有项目使用同一种包管理器。

### 性能

- 首次仓库扫描只建立轻量索引，不构建完整语义数据库。
- 相关文件检索优先使用 `rg`、文件名和依赖关系，后续再接 Tree-sitter/LSP。
- 默认限制单任务最大轮数、最大 Token、命令时长和补丁规模。

### 开源准备

- 产品代码、方案文档、第三方依赖、生成资产和评估数据必须有可追溯来源。
- 参考项目只能作为公开行为和架构研究来源，不能成为代码、Prompt、UI 或测试夹具的复制来源。
- 在发布前可以生成许可证清单、NOTICE 和 SBOM，并能说明每项第三方内容的分发条件。

## 7. 成功标准

MVP 需要在固定仓库集上稳定完成：

- 新增一个小型 API 或 CLI 功能。
- 修复一个可复现的失败测试。
- 审查一组包含已知问题的 diff。
- 为一个项目生成可运行脚手架。
- 对失败测试给出可定位、可复现、可审查的修复过程。

质量判断不只看“模型回复是否合理”，还要看测试通过率、无关修改量、审查误报率、运行成本、耗时和用户撤销率。

## 8. 明确非目标

- 第一版不做通用聊天机器人。
- 第一版不做自动合并、自动发布或自动生产部署。
- 第一版不做多租户云平台、计费和组织权限。
- 第一版不做浏览器自动化和桌面控制。
- 第一版不做复杂的多 Agent 协作。
- 第一版不复制 Blade Agent 的 Server/Runner 分布式拆分。
