# 路线图与评估

## 阶段 0：设计与基线

目标：冻结协议和安全边界。

- 确定 `Task/Run/Event/Tool/Approval` 类型。
- 完成 Windows/macOS/Linux 命令执行抽象。
- 建立 10 个固定仓库任务。
- 明确规则文件优先级和敏感路径策略。
- 决定独立仓库或 monorepo 子项目边界，并建立来源台账模板。
- 选定候选许可证，完成直接依赖和传递依赖的初步扫描。

## 阶段 1：MVP

目标：完成一次可靠的本地代码任务。

- CLI。
- `generate`、`review`、`fix`。
- 文件读取、搜索、补丁、Git diff、命令执行。
- Plan/Act、审批、checkpoint。
- JSONL 运行记录。
- 目标测试和有限修复循环。

退出条件：固定任务集中，至少大多数小型任务能生成可审查且测试通过的变更；失败任务能保留完整证据。

## 阶段 2：工程化

- `test` 模式。
- `scaffold` 模式和模板版本管理。
- 项目规则文件。
- CI 无头模式。
- 多 Provider 和模型预算。
- 轨迹回放和离线回归。
- 许可证扫描、SBOM 和第三方通知文件自动生成。

## 阶段 3：产品化

- 本地 Web 控制台。
- 运行历史、diff、日志和回滚。
- VS Code 集成。
- MCP/ACP 接入。
- Docker/远程执行后端。

## 评估任务集

| 类别 | 示例 |
| --- | --- |
| 生成 | 新增一个 REST API、CLI 子命令或数据模型 |
| 修复 | 修复确定性失败测试、边界条件或空指针 |
| 审查 | 注入权限、异常处理、并发和性能问题的 diff |
| 测试 | 为现有函数补单元测试和回归测试 |
| 脚手架 | 生成 Node、Python、Go 三种最小服务 |
| 维护 | 升级一个依赖并处理 API 变化 |

## 评估指标

- **Task success rate**：任务是否达到验收条件。
- **Test pass rate**：修改后目标测试和回归测试通过比例。
- **Patch precision**：无关修改行数占总修改行数的比例。
- **Review precision**：真实问题占审查发现的比例。
- **Review recall**：已知问题被发现的比例。
- **Recovery rate**：工具失败、测试失败或模型重试后恢复比例。
- **Human acceptance**：用户保留或撤销结果的比例。
- **Cost and latency**：Token、命令耗时和端到端耗时。

## 固定回归要求

- 同一任务保留输入、仓库 revision、模型配置和工具轨迹。
- 允许离线重放工具结果，避免每次评估都依赖网络。
- 测试基线和修改后结果必须同时记录。
- 任何“成功”结论必须可以从事件和命令结果中复核。
